# BITinvest

(изначально — BIT-Tinkoff-Invest-Bot)

Copy-trading мост между брокерскими счетами T-Bank Invest (бывш. Тинькофф
Инвестиции): состав портфеля одного или нескольких «master»-счетов
воспроизводится на «slave»-счёте — с нормировкой плеча и поддержкой шортов.

Осознанно развёрнут на **двух физически разных серверах** (parser-хост с
токенами master-счетов и executor-хост с токеном slave-счёта, обмен — через
`step.json` по HTTP): это не архитектурная случайность, а способ не попадать
под встроенную в Т-Банк платную систему автоследования.

Документ ниже расписывает **всю** торговую логику максимально подробно — это
намеренно избыточная детализация, чтобы не приходилось лезть в код ради
понимания «а что вообще происходит», и чтобы через полгода можно было сверить
поведение системы с тем, что задумывалось.

## Модель портфеля

Реализация: [`src/bitinvest/portfolio.py`](src/bitinvest/portfolio.py).

Портфель любого счёта (master или slave) — это набор знаковых позиций плюс
кэш. Знак важен: отрицательное количество — шорт, отрицательный кэш — деньги,
занятые у брокера (это и есть маржинальная торговля у Т-Банка: отдельной
ручки «плечо» нет, вы покупаете больше, чем у вас есть денег, брокер
покрывает разницу, разница и есть отрицательный кэш).

```
equity E   = кэш + Σ(quantity_i × price_i)     # знаковая сумма; E может быть меньше валовых позиций
w_i        = (quantity_i × price_i) / E         # знаковый вес позиции; шорт даёт w_i < 0
L          = Σ|w_i|                             # gross leverage — сумма модулей весов
w_cash     = 1 − Σw_i                            # тождество: кэш — всегда остаток, не хранится отдельной формулой
```

Рублёвая позиция (`RUB000UTSTOM`) трактуется как кэш, а не как обычная
позиция — это единственное, что вычитается из списка позиций и уходит в поле
`Snapshot.cash`. Другие валюты остаются обычными «позициями» (у них есть цена
в рублях через `current_price`, так что формулы выше работают без исключений).

`lot_size` каждой позиции не запрашивается отдельным вызовом API, а
восстанавливается из уже полученных данных: `quantity / quantity_lots`
(оба поля возвращает `get_portfolio()`). Знаки в числителе и знаменателе
совпадают, так что для шорта тоже получается корректный положительный
lot_size.

### Несколько master-счетов: смешивание весов

Если master-токенов несколько, их веса смешиваются в [`portfolio.blend()`](src/bitinvest/portfolio.py):

```
w_i^blended = Σ_t ( weight_t / Σweight ) × w_i^t
```

где `w_i^t` — вес позиции `i` **внутри** счёта `t` (то есть уже поделённый на
equity именно этого счёта). Смысл: заявленный вес токена — это **доля влияния
на итоговую аллокацию**, и ничего больше. Счёт с бо́льшим капиталом не получает
за это дополнительного веса.

Если одна бумага у одного мастера в лонге, а у другого — в шорте, веса
складываются знаково и могут взаимно погаситься (`blend()` отфильтровывает
результат с `|weight| < 1e-9` — такая бумага вообще не попадает в
`MasterView`, то есть слейв её не держит и не торгует).

## Нормировка плеча

Реализация: [`src/bitinvest/leverage.py`](src/bitinvest/leverage.py).

Плечо мастера (`L`, см. выше) нормируется **одним множителем на весь
портфель**, не по каждой позиции отдельно — это важно, потому что задача не
«поставь каждую бумагу под плечо 1», а «сохрани пропорции мастера, но чтобы
суммарное плечо не превышало заданное»:

```
k = target_leverage / L                          # "normalize": всегда ровно target
k = min(1, target_leverage / L)                   # "cap": target — потолок, не уставка
цель_i = k × w_i × E_slave
кэш_slave = остаток = E_slave − Σ|цель_i|·sign(w_i)   # ...точнее, E_slave × (1 − Σ k·w_i)
```

`policy = "cap"` — только сжимаем. Если мастер сам сидит в кэше (`L < target`),
это уважается: мы не станем доинвестировать за него. `policy = "normalize"`
(по умолчанию) — всегда выходим ровно на `target_leverage`, в том числе
разворачивая кэш мастера в позиции. Выбор `normalize` — результат A/B-теста
(`tools/ab_leverage_policy.py`, см. [`tools/ab-tests-documentation.md`](tools/ab-tests-documentation.md)):
`cap` заодно зеркалит каждое мелкое дневное колебание собственной экспозиции
мастера как реальную сделку у slave, `normalize` эту рябь гасит.

Примеры (подробный вывод, иллюстрирует механику `cap` — с `normalize` третья
колонка была бы всегда `1/L`, без потолка):

| портфель мастера | L | k при `target=1.0`, `cap` | что получает slave |
|---|---|---|---|
| A: 5·E, B: 3·E, кэш −7·E | 8 | 1/8 | A: 0.625, B: 0.375, кэш 0 — пропорция 5:3 внутри позиций сохранена |
| A: 0.5·E, кэш 0.5·E | 0.5 | 1 (упёрлись в потолок `min`) | A: 0.5, кэш 0.5 — кэш мастера не трогаем |
| A: +5·E, B: −3·E, кэш −1·E | 8 | 1/8 | A: +0.625, B: −0.375, кэш 0.75 |

Третья строка — «шорт как аналог фиата»: шорт открыт, суммарное плечо ровно
1.0, а заёмных денег на самом деле нет вообще (выручка от шорта осела в
кэше — кэш положительный несмотря на то, что позиция маржинальная). Шорт
**технически невозможен без маржинального счёта** (это требование брокера,
не этого бота), но он не обязан идти рука об руку с плечом больше 1 — ровно
поэтому нормировка идёт по сумме модулей весов, а не по каждой бумаге в
отдельности.

При `allow_short = false` шорт-ноги (`w_i < 0`) просто выбрасываются
(`leverage.drop_shorts()`) **до** вычисления `L` и `k`. Лонги при этом **не**
растягиваются, чтобы заполнить освободившуюся долю — это было бы уже нашей
инвестиционной идеей, а не мастера. Освободившаяся доля уходит в кэш.

## Маржа: предохранители

Реализация: [`src/bitinvest/margin.py`](src/bitinvest/margin.py),
используется в [`executor_service.py`](src/bitinvest/executor_service.py).

Т-Банк считает так:

```
начальная маржа (НМ)  = Σ |стоимость_i| × ставка_риска_i     # своя ставка для лонга и для шорта
минимальная маржа (ММ) = НМ / 2
ликвидный портфель (ЛП) ≥ НМ   → можно открывать новые позиции
ЛП < ММ                        → маржин-колл, принудительное закрытие
```

Ставки риска (`long_risk_rate` / `short_risk_rate`) запрашиваются пачкой через
`instruments.get_risk_rates()` по `instrument_uid` всех бумаг в цели. Так как
проектируемая НМ линейна по множителю `k` из раздела про плечо, предел для
`k` считается в замкнутой форме, без перебора:

```
k_margin = margin_safety × ЛП / Σ(|w_i × E_slave| × ставка_i)
k_итог   = min(k_желаемый, k_margin)
```

Запрос ставок риска и `margin_attributes` пропускается, если он заведомо не
может ничего ограничить: при чистых лонгах и `k·L ≤ 1` НМ не превысит equity,
потому что ставки риска не бывают больше 1 (`margin.needs_margin_check()`).
Это экономит один-два сетевых вызова на цикл в самом частом случае
(`mirror`/`accumulate` без шортов, плечо ≤ 1).

Если `funds_sufficiency_level` уже в жёлтой или красной зоне —
`executor_service` пишет об этом в лог отдельной строкой (`warning`/`error`),
но само по себе это не блокирует расчёт целей — блокирует именно нехватка
`k_margin`, если до неё дойдёт.

Каждый ордер, который требует маржи (шорт или суммарное плечо больше 1),
уходит с `confirm_margin_trade=True` — без этого флага такие ордера API
отклоняет. Перед тем как открыть или увеличить шорт по конкретной бумаге,
`trading.py` дополнительно проверяет `short_enabled_flag` через
`get_instrument_by()`: если брокер не разрешает шорт по этой бумаге, ордер
не выставляется вообще (лог-warning), а не падает с ошибкой API на исполнении.

## Режимы (`mode`)

Реализация: [`src/bitinvest/strategy.py`](src/bitinvest/strategy.py).

### `mirror`

Симметричный ребаланс: считаем цель в лотах для каждой бумаги (своей у
мастера или slave), сравниваем с тем, что реально держит slave, выставляем
разницу.

```
target_lots_i = truncate_to_zero( цель_i / (price_i × lot_size_i) )
order_i       = target_lots_i − current_lots_i
```

Округление — **усечение к нулю**, не floor. На отрицательных числах floor
округляет вниз (в сторону бо́льшего модуля) — цель «-2.4 лота» превратилась бы
в шорт на 3 лота вместо 2. Усечение всегда ошибается в сторону **меньшей**
позиции, что для лонга, что для шорта.

Если позиция должна перейти через ноль (например, было +50 лотов, а цель
теперь -45), ордер **разбивается на два**: закрытие текущей позиции и
отдельное открытие в другую сторону (`reason` в логе — «... (close)» и
«... (reverse)»). Причины две: во-первых, так честнее читается в логах; во-
вторых, составной ордер, пересекающий ноль, сложнее провести через
брокерские проверки по марже одним куском.

Позиции дешевле `min_order_value` не трогаем («пыль») — **кроме** любого
ордера, относящегося к полному закрытию позиции (см. «Ликвидация» ниже):
недокрытый хвост позиции, которой уже нет у мастера, хуже, чем заплатить
комиссию за маленькую сделку.

### `accumulate` (по умолчанию)

Дивидендный режим: покупать и держать, докупать редко и по делу, не
дёргаться на любое шевеление весов. Выбор дефолта — результат A/B-теста
(`tools/ab_mode_policy.py`, см. [`tools/ab-tests-documentation.md`](tools/ab-tests-documentation.md)):
`accumulate` впереди `mirror` по equity и в 4–7 раз дешевле по числу сделок,
подтверждено и на синтетике, и на реальных ценах. Порядок проверки по каждой
бумаге (`_plan_accumulate`):

1. **Позиции нет вообще (`current_lots == 0`)** → покупаем сразу всю цель
   («new position»). Это единственный случай в `accumulate`, где позиция
   открывается по текущему целевому весу мгновенно.
2. **Мастер вышел из бумаги полностью** (`figi not in targets`, то есть вес
   мастера по ней — ровно 0 или бумаги нет в `step.json`) → см. «Ликвидация».
3. **Мастер развернул позицию** (знак текущей и целевой позиции разный,
   `current_lots × target_lots < 0`) → это смена ставки, а не дрейф, идём в
   целевые лоты сразу, полностью, с разбиением через ноль как в `mirror`
   («reversal»).
4. **Перевес сверх порога**: `|current_value| > |target_value| × (1 +
   trim_threshold_pct/100)` → режем ровно до целевых лотов («trim»). Обычный
   дрейф цены внутри порога ордер не создаёт.
5. **Иначе** — позиция уже есть и в допуске → **ничего не делаем**, даже если
   целевой вес по бумаге вырос. Именно это — «не наращиваем то, что уже
   держим, просто потому что вес подрос»; докупка происходит только через
   раскладку свободного кэша (следующий раздел), не через рост целевого веса.

### Ликвидация: `liquidation_mode` (общее для `mirror` и `accumulate`)

Настройка: [`config.toml`](config.toml), поля `liquidation_mode` /
`liquidation_step_pct`. Реализация: `_liquidation_target()` /
`_liquidation_step()` в `strategy.py`, применяется в обоих режимах — в
`mirror` при `target_lots == 0`, в `accumulate` в пункте 2 списка выше.

Когда позицию нужно закрыть полностью (мастер её больше не держит), есть два
варианта:

- **`full`** — закрыть одним ордером сразу. Быстрее догоняем состав мастера,
  но весь объём уходит в рынок одним куском.
- **`gradual` (по умолчанию)** — закрывать по частям, за несколько циклов:

  ```
  шаг = max(1, ceil(|current_lots| × liquidation_step_pct / 100))
  wanted = 0                              если шаг ≥ |current_lots|
  wanted = current_lots − sign(current_lots) × шаг   иначе
  ```

  То есть каждый цикл продаётся (или откупается, если шорт) доля от **того,
  что держим сейчас**, округлённая вверх, но не меньше 1 лота — это гарантирует
  выход в ноль за конечное число циклов при любом размере позиции и любом
  проценте. При `liquidation_step_pct = 25` позиция закрывается примерно за
  4 цикла, ускоряясь в лотах по мере уменьшения остатка. Для совсем мелких
  позиций (доля от 25% меньше 1 лота) шаг всегда 1 лот.

**Почему по умолчанию `gradual`, а не `full`.** Идея: не сливать позицию одним
ордером, особенно в момент, когда счёт только переводят на автоследование и
на нём остаются легаси-позиции, которых у мастера никогда не было — резкая
распродажа всего сразу может дать плохую цену исполнения. `full` торгует
быстрее и точнее следует составу мастера, но платит за это потенциально
худшим исполнением на объёме. Решено A/B-тестом (`tools/ab_liquidation_policy.py`,
см. [`tools/ab-tests-documentation.md`](tools/ab-tests-documentation.md)):
`gradual` дешевле `full` в большинстве сценариев ликвидности (98–100% побед в
бакетах от средних позиций и выше, 62–86% на самых ликвидных), подтверждено
и на синтетике, и на реальных котировках. `liquidation_step_pct = 25` тоже
проверен A/B — из 10/25/40% дешевле по издержкам во всех бакетах ликвидности
одновременно.

Ордера, относящиеся к ликвидации (полной или частичной по graduated-схеме),
всегда проходят мимо фильтра `min_order_value` — форсированное закрытие
позиции не «опциональная» сделка, которую можно отложить как пыль.

### Раскладка свободного кэша (только `accumulate`): `deploy_free_cash`

Реализация: `_deploy_free_cash()` в `strategy.py`.

Без этого шага `accumulate` копил бы любые пополнения и дивиденды мёртвым
грузом до тех пор, пока мастер не откроет что-то новое.

```
investable = кэш_slave − Σ(запланированные ордера) − equity_slave × cash_buffer_pct / 100
```

Если `investable < min_order_value` — ничего не делаем. Иначе для каждой
бумаги, где цель больше того, что уже держим (с учётом уже запланированных
в этом цикле ордеров), считается разрыв `gap = target_value − held_value`, и
дальше по политике:

- **`never`** — раскладка вообще не запускается, деньги простаивают до
  появления новой позиции у мастера.
- **`underweight_first`** (по умолчанию) — бумаги сортируются по убыванию
  `gap`, и в каждую по очереди вкладывается `min(gap, investable)`, пока не
  кончится кэш или разрывы. Самый недовешенный получает всё, что нужно,
  первым.
- **`proportional`** — весь `investable` сразу распределяется между всеми
  разрывами пропорционально их размеру (`budget_i = investable × gap_i /
  Σgap`), исполняется в том же порядке по убыванию разрыва, но никто не
  получает приоритета — просто пропорция.

Ни при какой политике раскладка кэша не продаёт ничего другого ради этого —
только покупки на то, что и так простаивало. A/B-тест (`tools/ab_cash_policy.py`,
см. [`tools/ab-tests-documentation.md`](tools/ab-tests-documentation.md)):
`never` заметно хуже обоих активных вариантов, `underweight_first` и
`proportional` между собой статистически неотличимы — дефолт оставлен на
`underweight_first` за неимением разницы.

## A/B-тестирование

Семь офлайн-инструментов в `tools/`, все гоняют **настоящий**
`strategy.plan_orders()` / `bitinvest.margin` (не отдельную модель поверх),
чтобы сравнение было через тот код, который реально будет торговать:

- **`ab_mode_policy.py`** — `mirror` vs `accumulate`.
- **`ab_leverage_policy.py`** — `cap` vs `normalize`.
- **`ab_cash_policy.py`** — `never` / `underweight_first` / `proportional`
  для `accumulate.deploy_free_cash`.
- **`ab_liquidation_policy.py`** — `full` vs `gradual` для `liquidation_mode`,
  плюс сетка `liquidation_step_pct`, со случайными сценариями разной
  ликвидности и моделью market impact.
- **`ab_accumulate_tuning.py`** — сетки `trim_threshold_pct`,
  `cash_buffer_pct`, `min_order_value`.
- **`ab_margin_safety.py`** — сетка `margin_safety` через `bitinvest.margin`
  напрямую (единственный инструмент здесь, торгующий не через `plan_orders`).

Каждый умеет гонять и синтетику (случайное блуждание цены, фиксированный
сид, детерминированно), и реальные исторические котировки (T-Invest Sandbox
market data, 6 тикеров MOEX) — `tools/ab_runner.py`'s слот `real_basket` раз
в ~30 минут тянет одно реальное окно и прогоняет через все basket-сравнения
разом, экономя бюджет обращений к API.

Непрерывно крутится на сервере (`bitinvest-ab.service`, `tools/ab_runner.py`)
с 30.07.2026, копит статистику Уэлфорда (бегущее среднее/std, размер файла
не растёт со временем, переживает рестарт сервиса). Все вопросы, кроме
`margin_safety` (это выбор риск-аппетита, не оптимизация), **решены** и
отражены в `config.toml` по умолчанию — полный журнал с цифрами синтетика/
реальные данные по каждому тесту: [`tools/ab-tests-documentation.md`](tools/ab-tests-documentation.md).

## Формат обмена: `step.json`

Реализация: [`src/bitinvest/stepfile.py`](src/bitinvest/stepfile.py).

```json
{
  "schema": 2,
  "generated_at": "2026-07-28T12:00:00+00:00",
  "master_equity": 1234.5,
  "gross_leverage": 2.4,
  "cash_weight": -1.4,
  "positions": [
    {"figi": "...", "ticker": "...", "instrument_uid": "...",
     "lot_size": 10, "price": 123.4, "weight": 0.31}
  ]
}
```

Запись атомарная (пишется во временный файл, затем `rename` — executor
никогда не увидит наполовину записанный снимок). Если снимок старше
`max_step_age_sec` (по `generated_at`), executor **отказывается торговать**
(`StaleStepFile`) вместо того, чтобы бесконечно крутить последний известный
состав при упавшем parser-хосте.

## Исполнение ордеров

Реализация: [`src/bitinvest/trading.py`](src/bitinvest/trading.py).

Один `Client` (один gRPC-канал) на весь цикл, а не новый на каждый ордер.
Сначала выполняются все продажи, потом все покупки — чтобы к моменту покупок
максимально освободился кэш от продаж этого же цикла. `order_id` — `uuid4()`,
уникальный на каждый ордер. Ошибка на одном ордере (`try`/`except`, лог
`exception`) не прерывает цикл — остальные ордера всё равно выставляются, а
следующий цикл пересчитает состояние заново от реального портфеля, так что
пропущенный ордер самовосстановится.

`dry_run = true` в конфиге проходит весь путь — расчёт целей, лог каждого
ордера — но ничего не отправляет в сеть на исполнение.

## Установка

Библиотека `tinkoff-investments` в карантине на PyPI и не ставится. Используется
официальный преемник `t-tech-investments` (Т-Банк) с отдельного индекса, путь
импорта — `t_tech.invest` (было `tinkoff.invest`).

```bash
conda env create -f environment.yml
conda activate BITinvest
```

или через pip напрямую:

```bash
pip install -r requirements.txt
```

Из зависимостей осталась одна библиотека API: pandas выкинут, модель считается
на датаклассах.

## Настройка токенов

Токены создаются в личном кабинете T-Invest. **Обязательно** делать их
**account-scoped** (привязанными к одному конкретному брокерскому счёту), а не
full-profile — иначе при нескольких счетах под одним токеном ордер уйдёт не туда
(код предупреждает в лог и работает по первому счёту). Токен живёт 3 месяца с
момента последнего использования.

При первом запуске `scripts/autorun_*.sh` интерактивно спросят токены и сохранят
их в `secrets/` (`chmod 600`, не в аргументах командной строки — не светятся в
`ps aux`).

## Запуск

На parser-хосте:

```bash
BITINVEST_PUBLISH_DIR=/data/www ./scripts/autorun_parser.sh
```

На executor-хосте:

```bash
BITINVEST_STEP_URL=http://<parser-host>:8082/step.json ./scripts/autorun_executor.sh
```

Перед первым живым запуском имеет смысл выставить `dry_run = true` в
`config.toml`.

## Настройки (`config.toml`)

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `mode` | `accumulate` | `mirror` / `accumulate` |
| `target_leverage` | `1.0` | целевое суммарное плечо slave-счёта |
| `leverage_policy` | `normalize` | `cap` — потолок, `normalize` — точная уставка |
| `allow_short` | `true` | воспроизводить ли шорты мастера |
| `margin_safety` | `0.9` | доля ликвидного портфеля под начальную маржу |
| `min_order_value` | `1000.0` | ордера дешевле не выставляем (ликвидация — исключение) |
| `max_step_age_sec` | `900` | возраст снимка, после которого не торгуем |
| `dry_run` | `false` | считать и логировать, но не исполнять |
| `liquidation_mode` | `gradual` | `gradual` — по частям за несколько циклов, `full` — одним ордером |
| `liquidation_step_pct` | `25.0` | доля текущей позиции, закрываемая за цикл при `gradual` |
| `accumulate.deploy_free_cash` | `underweight_first` | `underweight_first` / `proportional` / `never` |
| `accumulate.cash_buffer_pct` | `0.0` | доля equity, не участвующая в раскладке кэша |
| `accumulate.trim_threshold_pct` | `25.0` | перевес, начиная с которого режем позицию |

## Известные ограничения

- Ровно **один slave-токен**. Ордера считаются против всего портфеля slave, так
  что второй токен просто проиграл бы тот же набор ещё раз. Executor падает с
  внятной ошибкой, если токенов больше.
- Ставки риска приходят как `Quotation`, и без живого токена в этой сессии
  единицы измерения подтвердить было нечем: значения больше 1.5 трактуются как
  проценты и делятся на 100. Проверить на реальном счёте.
- Плата за перенос непокрытой позиции (посуточная, по тарифной сетке) в расчёт
  целей не закладывается — держать плечо ночами дороже, чем выглядит.
- Рублёвый кэш считается кэшем; прочие валюты остаются обычными позициями.
- Модель market impact в `ab_liquidation_policy.py` — иллюстративная догадка,
  не откалиброванная по реальным данным (см. `tools/ab-tests-documentation.md`).

## Тесты

```bash
pytest tests/
```

Живых ордеров тесты не делают — только чистая логика на синтетических данных.
Полный прогон с реальными токенами — вручную, на песочнице/малых суммах.

А вот слив позиции, которой нет у мастера, ровно по 1 лоту за цикл —
**отдельная вещь и не баг**: это было намеренное решение (не дампить легаси-
позиции разом при переходе на автоследование), просто без настройки и без
масштабирования под размер позиции. В первой версии этого README (до
уточнения) обе вещи были по ошибке описаны как один и тот же дефект — это
неверно. Восстановлено и обобщено как `liquidation_mode = "gradual"` (доля от
текущей позиции за цикл вместо жёсткого 1 лота), с явной альтернативой
`"full"` и A/B-инструментом для сравнения, см. выше.
