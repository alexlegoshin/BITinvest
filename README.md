# BITinvest

(изначально — BIT-Tinkoff-Invest-Bot)

Copy-trading мост между брокерскими счетами T-Bank Invest (бывш. Тинькофф
Инвестиции): состав портфеля одного или нескольких «master»-счетов
воспроизводится на «slave»-счёте — с нормировкой плеча и поддержкой шортов.

Осознанно развёрнут на **двух физически разных серверах** (parser-хост с
токенами master-счетов и executor-хост с токеном slave-счёта, обмен — через
`step.json` по HTTP): это не архитектурная случайность, а способ не попадать
под встроенную в Т-Банк платную систему автоследования.

## Модель

Всё построено на трёх величинах, считаемых по каждому счёту:

```
equity E = кэш + Σ(знаковая стоимость позиций)   # кэш < 0 — это заём у брокера
w_i      = стоимость_i / E                        # знаковый вес, шорт даёт w < 0
L        = Σ|w_i|                                 # gross leverage
```

Плечо у Т-Банка — не настройка, а **следствие**: отдельной ручки нет, вы просто
покупаете больше, чем есть денег, а брокер докладывает разницу. Поэтому «плечо
мастера» — это его `L`, и нормируется оно **одним множителем на весь портфель**,
а не по каждой позиции отдельно:

```
k = min(1, target_leverage / L)        # policy = cap
цель_i = k · w_i · E_slave
кэш = остаток, ордером никогда не становится
```

Что из этого следует:

| портфель мастера | L | k при target 1.0 | что получает slave |
|---|---|---|---|
| A: 5·E, B: 3·E, кэш −7·E | 8 | 1/8 | A: 0.625, B: 0.375, кэш 0 — пропорция 5:3 цела |
| A: 0.5·E, кэш 0.5·E | 0.5 | 1 | A: 0.5, кэш 0.5 — кэш мастера уважаем, не доинвестируем |
| A: +5·E, B: −3·E, кэш −1·E | 8 | 1/8 | A: +0.625, B: −0.375, кэш 0.75 |

Третья строка — «шорт как аналог фиата»: шорт открыт, gross ровно 1.0, заёмных
денег нет вообще (выручка от шорта осела в кэше). Шорт **невозможен без
маржинального режима**, но вовсе не обязан идти с плечом — ровно поэтому
нормировка идёт по сумме модулей, а не по каждой бумаге.

При `leverage_policy = "cap"` целевое плечо — это **потолок**: мастера с плечом
8 ужимаем до 1, мастера, сидящего в кэше, не трогаем. `"normalize"` вытягивает
и вверх, доинвестируя кэш мастера своей волей.

### Предохранители по марже

Проектируемая начальная маржа (`Σ стоимость × ставка риска`, ставки лонг/шорт
берутся из `instruments.get_risk_rates()`) держится не выше `margin_safety` от
ликвидного портфеля. Так как маржа линейна по `k`, предел считается в замкнутой
форме и просто дополнительно ужимает множитель. Если `funds_sufficiency_level`
уже в жёлтой или красной зоне — это пишется в лог отдельной строкой.

Сетевые запросы за ставками риска делаются только когда они могут что-то
изменить: при чистых лонгах и `k·L ≤ 1` маржа заведомо меньше equity.

## Режимы

**`mirror`** (по умолчанию) — симметричное зеркало: догоняем целевые веса и
покупками, и продажами.

**`accumulate`** — дивидендный режим, ради которого всё изначально писалось:

- позицию, которая уже есть, **не наращиваем** просто потому, что её целевой
  вес подрос;
- позицию, которую мастер только что открыл, покупаем целиком;
- продаём только когда мастер реально сократился — и только за порогом
  `trim_threshold_pct`, чтобы обычный дрейф цен не гонял оборот;
- позицию, из которой мастер вышел, закрываем полностью и сразу;
- свободный кэш (пополнения, дивиденды) раскладываем в самые недовешенные
  позиции — никогда не продавая ради этого что-то другое.

Последний пункт — то, чего в v0.1 не было и без чего режим копил деньги
мёртвым грузом, пока мастер не откроет что-то новое. Сравнение политик:

```bash
python tools/ab_cash_policy.py
```

Детерминированный офлайн-прогон через тот же `strategy.plan_orders()`. Синтетика
показывает механику, а не вердикт — в шапке файла лежит TODO с планом прогона на
реальном ряде.

## Структура

```
src/bitinvest/
├── settings.py           # config.toml: режим, плечо, шорты, пороги
├── config.py             # токены/веса из secrets/, пути
├── broker.py             # общая обвязка API (MoneyValue -> float, выбор счёта)
├── portfolio.py          # знаковая модель: Position / Snapshot / MasterView
├── leverage.py           # нормировка плеча, чистая арифметика
├── margin.py             # ставки риска, начальная маржа, предохранители
├── strategy.py           # mirror / accumulate -> список ордеров
├── trading.py            # исполнение, dry-run, проверка права на шорт
├── stepfile.py           # step.json: запись, чтение, отказ по протуханию
├── parser_service.py     # entrypoint parser-хоста
└── executor_service.py   # entrypoint executor-хоста

scripts/                  # autorun-циклы для обоих хостов
tools/ab_cash_policy.py   # A/B кэш-политик
config.toml               # настройки исполнителя (секретов нет)
secrets/  data/           # в .gitignore
tests/                    # pytest, без сети
```

## Установка

Библиотека `tinkoff-investments` в карантине на PyPI и не ставится. Используется
официальный преемник `t-tech-investments` (Т-Банк) с отдельного индекса, путь
импорта — `t_tech.invest` (было `tinkoff.invest`).

```bash
conda env create -f environment.yml
conda activate bitinvest
```

или через pip напрямую:

```bash
pip install -r requirements.txt
```

Из зависимостей осталась одна библиотека API: pandas выкинут, модель считается
на датаклассах.

## Настройка токенов

Токены создаются в личном кабинете T-Invest. **Обязательно** делать их
**account-scoped** (привязанными к одному конкретному брокерскому счёту), а не
full-profile — иначе при нескольких счетах под одним токеном ордер уйдёт не туда
(код предупреждает в лог и работает по первому счёту). Токен живёт 3 месяца с
момента последнего использования.

При первом запуске `scripts/autorun_*.sh` интерактивно спросят токены и сохранят
их в `secrets/` (`chmod 600`, не в аргументах командной строки — не светятся в
`ps aux`).

**Вес master-токена — это доля влияния**, и ничего больше. Счёт с бо́льшим
капиталом не получает за это дополнительного веса: каждый счёт сначала
нормируется на собственный equity, и только потом счета смешиваются по
заявленным весам. В v0.1 эти две вещи перемножались, из-за чего заявленные веса
почти ничего не решали — если вы переносите старый `master_weights.txt`,
аллокация изменится.

## Запуск

На parser-хосте:

```bash
BITINVEST_PUBLISH_DIR=/data/www ./scripts/autorun_parser.sh
```

На executor-хосте:

```bash
BITINVEST_STEP_URL=http://<parser-host>:8082/step.json ./scripts/autorun_executor.sh
```

Executor отказывается торговать по снимку старше `max_step_age_sec` — если
parser-хост умер, лучше ничего не делать, чем крутить устаревший состав.

Перед первым живым запуском имеет смысл выставить `dry_run = true` в
`config.toml`: пройдёт весь расчёт и логирование, в сеть на исполнение не уйдёт
ничего.

## Настройки (`config.toml`)

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `mode` | `mirror` | `mirror` / `accumulate` |
| `target_leverage` | `1.0` | целевое суммарное плечо slave-счёта |
| `leverage_policy` | `cap` | `cap` — потолок, `normalize` — точная уставка |
| `allow_short` | `true` | воспроизводить ли шорты мастера |
| `margin_safety` | `0.9` | доля ликвидного портфеля под начальную маржу |
| `min_order_value` | `1000.0` | ордера дешевле не выставляем (полный выход — исключение) |
| `max_step_age_sec` | `900` | возраст снимка, после которого не торгуем |
| `dry_run` | `false` | считать и логировать, но не исполнять |
| `accumulate.deploy_free_cash` | `underweight_first` | `underweight_first` / `proportional` / `never` |
| `accumulate.cash_buffer_pct` | `0.0` | доля equity, не участвующая в раскладке кэша |
| `accumulate.trim_threshold_pct` | `25.0` | перевес, начиная с которого режем позицию |

При `allow_short = false` отрицательные веса просто отбрасываются, а лонги
**не** перенормируются вверх — освободившаяся доля уходит в кэш. Растягивать
лонги было бы уже нашей ставкой, а не мастера.

## Известные ограничения

- Ровно **один slave-токен**. Ордера считаются против всего портфеля slave, так
  что второй токен просто проиграл бы тот же набор ещё раз. Executor падает с
  внятной ошибкой, если токенов больше.
- Ставки риска приходят как `Quotation`, и без живого токена в этой сессии
  единицы измерения подтвердить было нечем: значения больше 1.5 трактуются как
  проценты и делятся на 100. Проверить на реальном счёте.
- Плата за перенос непокрытой позиции (посуточная, по тарифной сетке) в расчёт
  целей не закладывается — держать плечо ночами дороже, чем выглядит.
- Рублёвый кэш считается кэшем; прочие валюты остаются обычными позициями.

## История

Изначально (апрель 2025, `v0.1`) — прямолинейный прототип на официальной на тот
момент библиотеке `tinkoff-investments` (`tinkoff.invest`), с дублированным
кодом на двух хостах. Задумывался под дивидендную стратегию: покупать и
держать, изредка корректируя состав.

В июле 2026, после того как `tinkoff-investments` ушла в карантин на PyPI
(наследие переименования Тинькофф → Т-Банк — библиотеку переименовали не сразу,
официальный преемник появился только со временем), код реструктурирован и
перенесён на официальную библиотеку Т-Банка `t-tech-investments`
(`t_tech.invest`). Тогда же модель портфеля переписана со знаковых величин,
добавлены шорты, нормировка плеча и режим `accumulate`.

Отдельная археологическая заметка. В v0.1 дедбенд выглядел так:

```python
if (delta < delta * 0.75) or (delta > delta * 1.25):
```

При положительной `delta` (надо докупить) оба сравнения ложны, при
отрицательной — первое истинно. То есть уже имеющаяся позиция **только
урезалась и никогда не наращивалась**, а позиция, которой у мастера нет,
продавалась по одному лоту за цикл. Ровно та дивидендная логика, которая
задумывалась, но полученная опечаткой. Теперь это режим `accumulate` —
намеренный, с порогами и без посуточного слива по лоту.
