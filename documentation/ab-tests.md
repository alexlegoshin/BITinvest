# A/B-тесты: журнал и TODO

Место, куда результаты офлайн A/B-сравнений (запускаемых на сервере) кладутся
после прогона — чтобы не терялись между сессиями и чатами. Инструменты сами
живут в `tools/`, здесь — только записи о том, что прогнано, с какими
параметрами и что получилось.

Формат записи по каждому прогону: дата, коммит/версия кода, команда запуска,
сырые числа или путь к файлу с ними, и **вывод** — что из этого следует для
`config.toml` по умолчанию (если следует).

## TODO: `deploy_free_cash` — `never` vs `underweight_first` vs `proportional`

Инструмент: `tools/ab_cash_policy.py`

Вопрос: в режиме `accumulate`, куда девать простаивающий кэш (пополнения,
дивиденды), когда состав мастера не менялся — не трогать вообще (буквальное
поведение v0.1) или докладывать в отстающие позиции.

Статус: **не прогонялось на реальных данных**, только один демонстрационный
прогон синтетики в сессии, где инструмент писался (см. историю чата/README).
Синтетика показывает механику (never копит кэш мёртвым грузом, остальные
политики его пускают в дело ценой оборота и комиссий), но не даёт ответа на
вопрос "что лучше на практике".

Что нужно перед тем, как считать вопрос решённым:

- [ ] Прогнать `tools/ab_cash_policy.py` с реальным рядом цен (не случайным
      блужданием) — выгрузка `operations.get_operations()` по счёту мастера
      либо исторические свечи по его историческому составу.
- [ ] Прогнать на нескольких разных периодах (бычий/боковой/медвежий рынок
      отдельно), не только на одном сгенерированном ряде.
- [ ] Записать результат сюда: средний equity на конец периода по каждой
      политике, оборот, оценка комиссий, число сделок.

## TODO: `liquidation_mode` — `full` vs `gradual`

Инструмент: `tools/ab_liquidation_policy.py`

Вопрос: когда мастер полностью выходит из позиции, закрывать её у slave одним
ордером (`full`, быстрее догоняем мастера) или по частям за несколько циклов
(`gradual`, `liquidation_step_pct` за цикл, дефолт в `config.toml` — это
восстановленное осознанное поведение v0.1: избегать слива всей позиции разом,
особенно в момент перехода счёта на автоследование, когда там остаются старые
позиции, которых у мастера никогда не было).

Статус: **не прогонялось всерьёз**. В сессии, где инструмент писался, был
только smoke-прогон на 25 случайных сценариях для проверки, что скрипт вообще
работает и печатает разумные числа — это **не** аналитический прогон, вывода
из него делать нельзя.

Модель в инструменте — синтетическая (случайное блуждание цены + гипотеза
market impact `~ sqrt(объём ордера / средний дневной объём)`), константы
(`IMPACT_K`, `PERMANENT_FRACTION`) — угаданные, не откалиброванные. Полный
список TODO — в шапке `tools/ab_liquidation_policy.py`.

Что нужно перед тем, как считать вопрос решённым:

- [ ] Откалибровать `IMPACT_K`/`PERMANENT_FRACTION` по реальным данным
      (глубина стакана / исторические проскальзывания по интересующим
      тикерам), либо найти опубликованные оценки для российского рынка.
- [ ] Прогнать `tools/ab_liquidation_policy.py` с бо́льшим N (сотни-тысячи
      случайных сценариев) на сервере, не локально одним быстрым прогоном.
- [ ] Сузить диапазон размеров позиций в `make_scenarios()` до реалистичных
      для конкретного slave-счёта, а не широкого синтетического разброса.
- [ ] Проверить чувствительность к `liquidation_step_pct` (сейчас в A/B
      зафиксирован дефолт 25% — стоит прогнать сеткой значений).
- [ ] Записать результат сюда: по каждому бакету ликвидности (ratio позиции к
      среднему объёму) — что дешевле по издержкам, что быстрее.

## Как добавлять новую запись

1. Скопировать секцию выше как шаблон, заменить вопрос/инструмент.
2. Пока не прогнано — держать в TODO-секции.
3. После прогона на сервере — переносить сюда: дата, параметры запуска,
   агрегированные числа (или путь к сохранённому выводу, если объёмный),
   и явный вывод для `config.toml`.
